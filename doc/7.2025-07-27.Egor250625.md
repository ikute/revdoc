### Структура проекта

1. Как-будто монорепозиторий больше минус, чем плюс, если ты делаешь микросервисы.
Как минимум у всех сервисов будет общая гит-история и релизные теги, а ну и CI/CD было бы проще настроить под каждый проект,
чтобы при изменении одного сервиса не нужно было бы билдить сразу все. Для простоты, можно и в монорепе сделать.

_Если хочется как-то объединить все репозитории в один проект, то можно создать организацию (это бесплатно) на гитхабе под проект_

2. У твоего проекта нет истории, все за один коммит сделал, нужно привыкать работать с гитом, потому что все равно придется.
Самое простое - можно было создать под каждый сервис по ишью и работать по гитхаб-флоу
(main -> task/task-name -> release/task-name -> main). Можно и на задачи поменьше нарезать,
но желательно делать это вертикально по фичам. Например, задача на логин/регистрацию пользователей,
но не задача на создание сущностей хибернейта. Нарезать лучше по фичам, потому что на работе все задачи будут примерно такими.

_Все неудачные коммиты легко можно пофиксить через squash (rebase -i), тем более в идее это легко делается через интерфейс_

3. Не нужно перекладывать на пользователей сборку проекта и отмечать докерфайлы в гитигноре. Не совсем понял, в чем была мотивация.

### Архитектура

1. С проектированием сервисов я бы поспорил.
Хоть работать с кафкой можно как угодно, но каноничный способ (асинхронный) стоит знать хотя-бы для прохождения собеседований:
кафка - это просто лог, куда мы записываем события, которые произошли в системе,
а далее система должна каким-то образом реагировать на эти события.
По возможности стоит определять события так, чтобы они отображались на процессы бизнеса, так система будет более гибко реагировать на события.
Вот, к примеру, при создании пользователя ты отправляешь в кафку запрос на отправку электронного сообщения (WELCOME_EMAIL_TYPE).
Правильно было бы сделать так: при создании пользователя логируем в кафку событие UserRegisteredEvent,
подписываем сервис нотификации на соответствующий топик, далее после получения события о регистрации на стороне
сервиса нотификации уже генерируем и отправляем письмо. В таком случае наш апи-сервис вообще ничего не знает о том,
как система отреагирует на событие (ну и это правильно как-бы).

Что касается технички, то по стандарту нужно создавать топики под сущность и указывать идентификатор
(естественный или сгенерированный) в качестве ключа, так кафка гарантированно запишет сообщения с одинаковым ключем
в одну и ту же партицию, что дает нам гарантию порядка сообщений с одинаковым ключем.

В метаданных сообщений желательно указывать версию, таким образом мы оставляем себе возможность делать ломающие изменения в схеме сообщения:

```json
{
    "event": "TYPE"
    "schema": "v1",
    "timestamp": 123456,
    ...
}
```

C учетом этого вот как бы я спроектировал систему:
- api-service оставляем, как есть (хотя его тоже можно распилить на id-api и task-api, но я бы не парился).
    Он будет продюсить события по изменениям в юзерах и задачах в кафку.
- analyticts-api будет собирать дневные отчеты по задачам. Подписываем его на изменения задач, аналитику собираем в
    постгрес и по крону делаем рассылку (либо через события в кафке, либо по ресту).
- notification-api отвечает за отправку уведомлений по различным каналам связи (у нас тока email).
    Подписываем на аналитику (если через кафку) и на изменения юзеров. Если нам нужна гарантия доставки уведомлений,
    то используем базу, как очередь и предварительно складываем все уведомления в табличку. Зачем еще одна очередь,
    если есть кафка? Чтобы оставить себе возможность отправлять уведомления не по порядку, если при обработке одного
    из них возникли траблы и мы хотим попробовать отправить его позже. Впрочем, через кафку это тоже можно организовать
    через dead letter queue.

_Поскольку это учебный проект, то не обязательно на каждый сервис поднимать свой инстанс постгреса,
достаточно создать базу (CREATE DATABASE) данных для каждого сервиса в рамках одного инстанса
(чтобы нельзя было сделать кросс-запросы) и таким образом эмулировать поведение распределенной системы_

5. При создании пользователя ты сразу отправляешь сообщение в кафку. Для начала, не стоит отправлять сообщения в кафку
во время sql-транзакции, также как и делать запросы по http. Но главная проблема тут - ты пытаешься объединить в транзакцию
и создание пользователя и отправку сообщения в кафку. В общем случае это может привести систему в неконсистентное состояние,
потому что невозможно гарантировать, что данные одновременно запишутся в постгрес и отправятся в кафку.
Хотя в твоем случае как-будто по эксепшену транзакция должна (но не факт, что сработает) откатиться, но вот зависимость
создания пользователя от состояния кафки делает этот запрос не отказоустойчивым.

Тут тебе нужно изучить outbox-паттерн, который закрывает подавляющую часть проблем с гарантиями доставки и поэтому
применяется очень часто. Его суть в том, что мы не отправляем сообщение в кафку сразу при создании пользователя,
сначала мы в рамках одной транзакции создаем нового пользователя и записываем событие в отдельную таблицу (ее нужно заранее создать).
Далее напишем скедуллер, который будет брать неотправленные сообщения из таблицы с эвентами и перекладывать их в кафку,
причем мы пытаемся отправить сообщение до тех пор пока оно не отправится. Ну и все - проблему пофиксили.

Таблица с эвентами может выглядить так:

```sql
CREATE TABLE task_tracker.user_events (
    id              SERIAL      PRIMARY KEY,
    pull_count      INTEGER     DEFAULT 0 NOT NULL,                     -- Количество чтений события (или попытки отправить сообщение в кафку)
    enqueued_at     TIMESTAMP   DEFAULT CURRENT_TIMESTAMP NOT NULL,     -- Время записи события в очередь (просто для мониторинга)
    reserved_to     TIMESTAMP   NOT NULL,                               -- Запланированное время отправки сообщения (используется для возможности отправлять сообщения вне транзакции и для возможности отложить отправку сообщения при неудачной попытке)
    message         JSONB       NOT NULL                                -- Тело сообщения в формате json
);
```

Достаем сообщения из таблицы с эвентами так:

```sql
WITH chunk AS (
    SELECT ue.id
    FROM task_tracker.user_events ue
    WHERE ue.reserved_to <= CURRENT_TIMESTAMP
    LIMIT :limit
    FOR UPDATE SKIP LOCKED -- Пропускаем сообщения, которые уже пытаемся обновить, чтобы не читать одни и те же сообщения при наличии нескольких реплик приложения (многопоточка, все дела)
)
-- Заранее обновляем запланированное время отправки. Delay выбираем так, чтобы хватило времени на отправку сообщения в кафку и на удаление/перенос в архив записи из таблицы. Теперь можно не ставить @Transactional, дубликации сообщений почти всюду не будет
UPDATE task_tracker.user_events ue
SET
    reserved_to = CURRENT_TIMESTAMP + :delay_seconds * INTERVAL '1 second',
    pull_count = ue.read_count + 1
FROM chunk c
WHERE ue.id = c.id
RETURNING ue.id, ue.read_count, ue.pull_count, ue.message;
```

Самое важное - не пытаемся одновременно записать и в постгрес и в sql_

6. По ресту есть пара замечаний.

У эндпоинтов странный и не единообразный нейминг. Проще всего делать ручки по общепринятому шаблону, чтобы апи был интуитивно понятен:
- GET /tasks[?filter=*&page=*&limit=*] - получить список всех задач пользователя
- GET /tasks/{id} - получить задачу в детальном виде по айди
- POST /tasks - создать задачу
- PUT /tasks/{id} - безусловно обновить задачу (поменять название, описание и т.д.)
- PATCH /tasks/{id} - для обновления параметров, где присутсвует бизнес-логика (у нас - это переходы по статусам)
- DELETE /tasks/{id} - удалить задачу по айди

- GET /users/me - текущий аутентифицированный пользователь (используем алиас 'me' для единообразия, потому что других пользователей мы раскрывать не хотим)
- POST /users - регистрация нового пользователя.

- POST /access-tokens - получить токен аутентификации (логин крч).

Второй момент, что ты не отдаешь в ответе полную информацию по задачам. Клиенты ничего не знают про статусы,
поэтому на фронте их нужно хардкодить, по итогу имеем дублирование кода и сложность внесения изменений по статусам.
Исправить это достаточно просто - нужно вместе с задачами возвращать статусы, в которые можно задачу перевести:

```json
{
    "id": 1,
    "title": "Название",
    "description": "Описание...",
    "status": "STATUS",
    "possibleStatuses": [
        ...
    ]
}
```

Ну и ошибки недостачно информативные. Клиент должен понимать где произошла ошибка, в чем она заключается ошибка и как ее можно исправить.
В [RFC-9457](https://www.rfc-editor.org/rfc/rfc9457.html) описан базовый шаблон для ошибок в ресте, плюс спринг 3 его поддерживает через опцию mvc.problemdetails
