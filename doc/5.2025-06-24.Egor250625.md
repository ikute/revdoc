### Билд

По билду почти все ок, кроме того, что ты не структурируешь зависимости. Управлять зависимостями в проекте будет сильно проще,
если знать для чего они используются. Вот пример:

```groovy
dependencies {
    // platform
    implementation 'org.springframework.boot:spring-boot-starter'

    // web
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
    implementation 'org.springframework.security:spring-security-crypto:6.2.1'

    // db-client
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'
    runtimeOnly 'org.postgresql:postgresql'

    // migration-tool
    implementation 'org.liquibase:liquibase-core'

    // validation-tool
    implementation 'org.springframework.boot:spring-boot-starter-validation'

    // mapping-tool
    annotationProcessor 'org.mapstruct:mapstruct-processor:1.4.2.Final'
    implementation 'org.mapstruct:mapstruct:1.4.2.Final'

    // lombok-tool
    annotationProcessor 'org.projectlombok:lombok'
    compileOnly 'org.projectlombok:lombok'

    // testing
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
    testRuntimeOnly 'org.junit.platform:junit-platform-launcher'
}
```

_В общем, использовать градле - это верное направление*_

9.
Использовать lat: double и lon: double в качестве естественного ключа - это скорее неудачное решение,
потому что насколько я помню апишка каждый раз возвращает отличающиеся координаты для локаций.
Поэтому ты каждый раз вынужден проверять, что координата из бд отличается от переданной на eps.
Тут есть вероятность, что выбранной точности тебе не хватит и локация не удалится.

Как вариант ты можешь использовать идентификатор локации в качестве ключа.
Для этого после извлечения погоды из апишки тебе достаточно подставлять идентификатор из бд перед тем, как вернуть ответ.

_Просто к слову, если ты не занимаешься сложными математическими вычислениями, то лучше считать,
что double - ридонли, поскольку при любой операции будет накапливаться ошибка_

### Форматирование

Заметил что в проекте есть проблемы с форматированием.

Советую настроить автоформатирование через идею:
- Settings -> Tools -> Actions on Save -> Reformat Code (Changed Lines) - при сохранении файла идея будет автоматически форматировать код.
- Settings -> Tools -> Actions on Save -> Optimize imports - при сохранении файла будет фиксить импорты (например, удалять неиспользуемые)
- Settings -> Editor -> Code Style -> Java (Class count to use import with *: 99 и Names count to use static import with *: 99) - просто потому что в джаве принято не использовать вайлдкард импорты (хотя в котлине, наоборот, принято все импорты вайлдкардить).
