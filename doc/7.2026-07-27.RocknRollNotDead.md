## 1. Структура проекта (в целом)

1.1. CI/CD скрипты можно было вынести в отдельный репозиторий, сейчас в каждом сервисе лежит идентичный build.yml. В
отдельном репозитории можно написать обобщенные sh-скрипты и чекаутить их во время билда в github-workflows.

```sh
#!/usr/bin/bash
# Build & push image
# Локальные опции прокидываем через переменные окружения

REMOTE_REPOSITORY=${REMOTE_HOST}/${IMAGE_NAME}

docker build --tag ${IMAGE_NAME} .

docker tag ${IMAGE_NAME}:latest ${REMOTE_REPOSITORY}:${VERSION}
docker tag ${IMAGE_NAME}:latest ${REMOTE_REPOSITORY}:latest

docker image push --all-tags ${REMOTE_REPOSITORY}
```

Ну и тесты лучше также запускать в докер-контейнере с тем же окружением, на котором будет запускаться приложение, а не
в окружении workflows-агента. (Иначе девопс ругаться будет).

1.2. Схему сообщений в кафке можно версионировать, чтобы можно было мигрировать на новую версию с ломающими изменениями.

2.7. Task связана с User как @ManyToOne(LAZY). При запросе списка задач не делаешь явного join-fetch к пользователю
(несмотря на то, что запрашиваются задачи для одного пользователя, это все равно n+1). Главная проблема тут, что это не
так просто заметить, потому что `::getOwner()` вызывается в маппере.

```java
@Getter
@Entity
@Table(name = "tasks")
public class Task {

    @JoinColumn(nullable = false)
    @ManyToOne(fetch = FetchType.LAZY)
    private User owner;

    // ...
}

@Repository
public interface TaskRepository extends JpaRepository<Task, Long> {

    List<Task> findByOwnerIdOrderByTimestampDesc(Long ownerId);
}

public List<TaskDto> get(Long userId) {
    // Достаем задачи без join-fetch
    List<Task> tasks = taskRepository.findByOwnerIdOrderByTimestampDesc(userId);
    return TaskMapper.mapList(tasks);
}

public TaskDto map(Task task) {
    return new TaskDto(
            task.getId(),
            task.getName(),
            task.getText(),
            UserMapper.execute(task.getOwner()), // <-- Делаем +1 запрос за овнером
            task.getStatus(),
            task.getTimestamp());
}
```

3.4. Спорное решение использовать `offset.earliest` в конфиге кафки. Если вдруг кафка потеряет оффсет у консьюмер
группы, то все доступные записи в кафке будут заново обработаны (будешь спамить древними письмами, которые уже могли
быть обработаны). В целом можно и такую опцию оставить, но в таком случае нужно писать механизм дедубликации (и

через неделю). Ну или для безопасности тут можно было использовать `offset.latest`, тем более если гарантия доставки не

### Тесты (src/test)

3.7. Из тестов лучше убрать функцию `::shouldSend2messagesNoRaceConditions` (ну или переименовать). Этот тест исполняется
в одном потоке последовательно. Опция `concurrency` в кафке отвечает за то, сколько потоков (консьюмеров в группе) будут
читать записи из кафки. Если в качестве ключа ты используешь userId, то сообщения будут записываться/читаться упорядоченно
для пользователя (и этого вполне достаточно, не обязательно нужно читать в одном потоке).

```java
@Test
void shouldSend2messagesNoRaceConditions() {

    // Последовательно консьюмишь два сообщения с письмами:
    kafkaConsumer.consume(objectMapper.writeValueAsString(new EmailDto(
            EMAIL1, HEAD_1, TEXT1)));
    kafkaConsumer.consume(objectMapper.writeValueAsString(new EmailDto(
            EMAIL2, HEAD_2, TEXT2)));

    ArgumentCaptor<SimpleMailMessage> captor = ArgumentCaptor.forClass(SimpleMailMessage.class);
    verify(mailSender, times(2)).send(captor.capture());

    assertThat(captor.getAllValues())
            .extracting(SimpleMailMessage::getTo)
            .containsExactly(new String[]{EMAIL1}, new String[]{EMAIL2});
}
```
