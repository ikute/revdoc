user/entity и location/entity.

Связь @OneToMany юзера с локацией это какой-то локальный мем? Если эта связь нигде не используется, то ее нужно выпилить.

Самое сложное при работе с хибернейтом - это держать в голове запросы, которые выполнятся под капотом,
поэтому хорошей практикой будет вообще не делать связи (@ToOne и @ToMany) между сущностями и использовать вместо
них ссылки (по id). И тем более не стоит делать связи @ToMany с потенциально бесконечными коллекциями,
потому что слишком легко можно получить cross-join при очередном join fetch запросе.
(Только потом прочитал, что количество локаций для пользователей ограничено)*

Связи лучше использовать только для композитных аттрибутов сущности. Пусть к примеру есть две таблички
todo.tasks и todo.task_statuses, очевидно, что статус является аттрибутом задачи
(просто потому, что в отдельности статус всего лишь описывает свойство задачи).
В таком случае можно использовать связь*:

```java
@Entity
@Table(schema = "todo", name = "tasks")
class Task {

    @Id
    private int id;

    @Column
    private int assigneeId;

    @OneToOne(by = "status_id")
    private TaskStatus status;

    @Column
    private String name;
}
```

```java
@Entity
@Table(schema = "todo", name = "task_statuses")
class TaskStatus {

    @Id
    private int id;

    @Column
    private String alias;
}
```

_По моему опыту это самый простой и главное наглядный способ работать с хибернейтом_

Каждый сервис должен отвечать за отдельный и независимый процесс, поэтому не нужно переиспользовать сервисы в сервисах.

В разных сервисах зачастую может повторяться одинаковый кусок логики (особенно в больших проектах) и есть соблазн
его переиспользовать. Но из-за того, что разные процессы не зависимы друг от друга, то и их логика будет меняться не зависимо.
Так что чистый код тут игнорируем, чтобы не переписывать потом пол проекта.
К тому же на бэке самое важное - это понимать где, когда и сколько делается запросов и гораздо проще найти эту информацию
в методе на 100 строк, чем прыгать по стектрейсу через весь проект.*

_От того, что ты размажешь сложный бизнес-процесс по разным сервисам проще он не станет*_

17. Если ты используешь @Transactional(readOnly), то все запросы будут выполняться на одном соединении,
тогда как без него это как повезет. Проаннотированные методы будут более предсказуемо использовать ресурсы,
но при этом соединение будет открыто через прокси до вызова метода.
Т.е. если запрос всего один - то аннотацию лучше не использовать, если больше одного запроса - то 50/50
